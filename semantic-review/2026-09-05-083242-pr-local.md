# Financial event pairing with incomplete replay and provenance boundaries

The change routes currency through an atomic ledger/audit writer, but several source boundaries still fail the Spec 53 contract. Request-driven economy endpoints derive the financial identity only after they have created or advanced the domain object, so a client retry becomes another purchase, upgrade, or refinement instead of returning the original result. Placement-mode battle events aggregate money by stable while discarding the per-robot placement facts that produced the aggregate, and the rollout guard permits the new paired records before a `Cutover_Cycle` exists. **Watch for:** **confirmed** production defects in request replay suppression, stable-level reward provenance, and forward-only cutover enforcement; **confirmed** test-only blind spot in the direct-writer guard.

**Verdict**: NEEDS_CHANGES

## High-level view

Request operations have no durable client/request identity. Their financial event IDs are derived from a newly inserted inventory/robot/refinement row or the newly calculated target level, so the same request after a lost response is interpreted as a fresh economy action and can spend credits again.

KotH and Grand Melee aggregate battle income per stable, but the persisted breakdown reduces that aggregate to a single amount. In Grand Melee it records the first robot placement for a stable that may have several participating robots; in KotH it does not record any placement. The amount cannot be explained from its stored inputs.

The forward-only state is modeled, but the credit service only rejects an inactive *post-cutover* state. Before the cutover is recorded, it still writes the new financial pair, blurring the Legacy_Record boundary the rollout is meant to protect.

The direct-writer scanner catches the present direct object-literal form only. It is a regression-test/rollout-gate weakness rather than a current money-writing defect, but it cannot enforce the stated “no new direct writers” invariant against ordinary refactors.

<details>
<summary>Issues (4)</summary>

1. **Request retries can repeat spending** — **confirmed, production defect.** Persist or accept a request idempotency key before changing the domain state, then reuse it for the financial event and return the original operation result on retry.
2. **Placement-mode aggregates lose amount-affecting facts** — **confirmed, production defect.** Persist every contributing placement/reward component (or a faithful stable aggregate) for KotH and Grand Melee instead of substituting the total as a participation floor or selecting one robot’s placement.
3. **The paired path is active before the Cutover_Cycle** — **confirmed, production defect.** Make the pre-cutover path explicitly legacy/non-paired, or block deployment activation until the durable cutover is recorded; do not emit post-contract identities in the pre-cutover period.
4. **Direct-writer coverage misses indirect Prisma data objects** — **confirmed, test-only verification gap.** Extend the AST analysis to resolve object variables/spreads or enforce at Prisma-call level so a refactor cannot add an uncovered `User.currency` write.

## Request identities are created after the operation they should deduplicate

**Confirmed, production defect.** Spec 53 requires request-driven purchases, upgrades, sales, refinements, and creation to retain or propagate a durable source identity across retries. The API schemas expose no idempotency key, and the transaction code creates its financial identity from state that did not exist before this attempt. `app/backend/src/routes/weaponInventory.ts:309-349` inserts `weaponInventory` and then uses its new ID for `weapon_purchase`; `app/backend/src/routes/weaponInventory.ts:838-852` creates the refinement slot before building the refinement identity. A response-lost retry therefore creates another inventory item or the next refinement slot and emits a distinct pair.

The same behavior exists for upgrades. `app/backend/src/routes/facility.ts:271-322` derives `facility_upgrade` from `facilityType-targetLevel` after re-reading the current level, so replaying a completed request upgrades and charges the next level. `app/backend/src/services/robot/robotUpgradeService.ts:340-393` updates the robot before deriving an identity from the just-applied level transitions. Robot creation likewise derives `robot_creation` from the newly created robot ID at `app/backend/src/services/robot/robotCreationService.ts:160-179`; a retry does not return the committed operation. Row locks serialize competing requests but do not identify them. Create a persisted request-operation record or accept a validated idempotency key, reserve it before the domain mutation, and retrieve the original completed response when it repeats.

## Stable battle-income rows do not retain the placement components they aggregate

**Confirmed, production defect.** In `app/backend/src/services/grand-melee/grandMeleeBattleOrchestrator.ts:449-503`, `creditsByUser` sums every robot reward, but the row records that sum as `participationFloor`, records `winComponent: 0`, and obtains `placement` from only the first matching participant. A stable with multiple Grand Melee entrants therefore stores a placement that need not explain any part of the total and omits all other placements.

KotH has the same loss of provenance: `app/backend/src/services/koth/kothBattleOrchestrator.ts:446-500` aggregates all robot rewards per user, then labels the aggregate as a participation floor with no placement field. The breakdown validator in `app/backend/src/types/financialTypes.ts:225-236` accepts this shape, so the incomplete facts become durable. This violates the requirement that later reporting explain amounts from recorded battle tier/outcome/placement/team-size facts without consulting participant records or current formulas. Store a per-robot reward/placement component list in the stable-level breakdown, or extend the stable breakdown with a deterministic aggregate that includes every contributing placement and reward component.

## Cutover state does not stop paired writes before authority begins

**Confirmed, production defect.** `app/backend/src/services/financial/creditMutationService.ts:334-343` calls `assertRequiredCaptureForCycle` and immediately writes the new balance/ledger/audit pair. The guard at `app/backend/src/services/migration/financialRollout.ts:264-277` throws only when `classifyCycle` is `post_cutover` *and* capture is inactive. With the default rollout state (`cutoverCycle: null`), every cycle is `pre_cutover` and the guard succeeds; migrated writers therefore emit rows carrying `financialEventId` before `recordAccCutover()` records an authoritative cycle.

That makes new pre-cutover rows neither untouched legacy history nor authoritative post-cutover evidence, contrary to the Forward_Only_Cutover boundary. Separate the legacy/pre-cutover writer behavior from `Credit_Mutation_Service`, or make the capture path unavailable until the rollout has both activated capture and recorded `Cutover_Cycle`. The same decision must cover prestige records if their evidence boundary is intended to start at cutover.

## The direct-writer gate is narrower than the mutation invariant

**Confirmed, test-only verification gap.** `app/backend/src/services/migration/directWriterCoverage.ts:85-113` reports `currency` only when the property appears inside an object literal used directly as a `data` property. It misses equivalent code such as `const data = { currency: { increment: amount } }; tx.user.update({ where, data })`, a spread-built `data` object, or a helper result. The manifest test (`app/backend/tests/coverageManifest.test.ts:60-74`) therefore proves only that the current syntax has four expected matches, not that future production code cannot introduce a direct credit write.

No current production bypass was identified, but the required blocking coverage check is bypassable by a routine refactor. Resolve identifiers and object spreads through the TypeScript checker, or match `user.update` calls and inspect the referenced initializer graph; add regression tests for each indirect form.
